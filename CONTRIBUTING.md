# Contributing to KAMLESH & SONS OS

Thank you for contributing to **KAMLESH & SONS OS (K&S OS)**.

K&S OS is the living operating system of KAMLESH & SONS. Contributions should improve the company's knowledge, systems, standards, and ability to execute consistently.

## 1. Core Principle

> **Chat is for brainstorming. GitHub is the official record.**

Important decisions, processes, standards, and innovations should be documented in the repository rather than remaining only in conversations.

## 2. Before Making a Change

Before creating or modifying content:

1. Review the existing repository structure.
2. Search for related documentation.
3. Preserve existing decisions and useful work.
4. Check whether an existing document should be updated instead of creating a duplicate.
5. Identify related decisions, innovations, roadmap items, and documents.

## 3. Documentation Standards

New documents should use clear, descriptive filenames and should be placed in the appropriate section of the repository.

Where applicable, documents should include:

- Document ID
- Title
- Version
- Status
- Owner
- Created date
- Last updated date
- Related documents
- Related decisions
- Related innovations
- Change history

## 4. Decision Records

Significant strategic, operational, financial, technology, brand, or architectural decisions should receive a unique `DEC-*` identifier.

Examples:

- `DEC-0001` — Company Name
- `DEC-0002` — Brand Positioning

Do not silently change an established decision. If a decision changes, document the new reasoning and update affected references.

## 5. Innovation Vault

New ideas with potential strategic, customer, operational, or technological value should be tracked in the Innovation Vault using an `INV-*` identifier.

An idea does not automatically become a commitment. The Innovation Vault exists to preserve and evaluate ideas before implementation.

## 6. Meetings

Important meetings and planning sessions should be captured using the meeting template where appropriate.

A meeting record should normally contain:

- Agenda
- Discussion
- Decisions
- Action items
- Owners
- Next steps

## 7. Cross-Referencing

Documentation should be connected rather than isolated.

When relevant, link to:

- Related documents
- Decision records
- Innovation records
- Roadmap milestones
- Architecture documents
- Meeting records

## 8. Versioning

K&S OS follows **Semantic Versioning** for releases:

`MAJOR.MINOR.PATCH`

In general:

- **MAJOR** — major operating-model or compatibility change.
- **MINOR** — meaningful new capability or documentation area.
- **PATCH** — corrections, clarifications, and small improvements.

The `VERSION` file and `CHANGELOG.md` must remain consistent with releases.

## 9. Commit Messages

Use clear conventional-style commit messages.

Examples:

```text
feat(ai): add AI Concierge architecture

docs(brand): add typography standards

docs(decisions): add DEC-0002 brand positioning

fix(docs): correct roadmap references

chore: update repository metadata
```

Commits should describe the purpose of the change, not merely the file name.

## 10. Quality Standard

Before submitting a change, verify that:

- The content is accurate and intentional.
- Existing work has not been unnecessarily duplicated or removed.
- Links and references are correct.
- Related documentation has been considered.
- Decision and innovation records are updated when required.
- Versioning and changelog requirements have been considered.

## 11. Strategic Changes

A major change should include a repository impact assessment covering, where relevant:

- Company strategy
- Brand
- Customer experience
- Technology
- Operations
- Finance
- AI
- Expansion
- Existing decisions
- Innovation initiatives

## 12. Working Model

K&S OS is a living system. Documentation should evolve as the company learns.

The objective is not to create documentation for its own sake. The objective is to preserve institutional knowledge, make decisions traceable, improve execution, and build systems that can scale with KAMLESH & SONS.
